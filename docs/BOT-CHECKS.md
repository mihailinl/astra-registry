# What the registry bot checks

> Generated by `bot/gen-checks-doc.mjs` from `bot/lib/codes.mjs`. Edit the
> prose in the generator and the codes in `codes.mjs`; do not edit this file.

`bot/ingest.mjs` is what makes a stranger's release listable without anyone
reading it. This is the list of everything it decides, the fixed code each
decision produces, and — the half that matters more — what it does **not**
decide.

## The shape of the thing

A submitter supplies **two facts**: a repository and a release tag. Everything
else — the id, the version, the display name, the summary, the licence, the
capabilities, the permissions, the platforms, the digests, the sizes — is read
out of the `.astraplugin` bundle attached to that release.

That is not a convenience. Everything read out of the bundle is covered by the
build attestation, which makes it strictly more trustworthy than anything a
person typed into a form. It also deletes a whole class of rejection: there is
no "your form disagrees with `plugin.toml`" here, because there is no form to
disagree with. The two facts that *are* typed are exactly the two the bundle
cannot vouch for, and both are checked against GitHub rather than believed.

## What never reaches this bot

The built-in sidecars — `builtin_stt`, `astra-vox` — are real plugins in the
daemon's one plugin map, with the same lifecycle and the same health monitor as
anything installed from here. They differ only in provenance: their manifest is
built in memory, nothing is written under `<plugins_dir>`, and
PRODUCTION_PLAN §5.5 gives them a code-declared grant set with **no trust
record and no disk read**. There is no bundle, no release, no digest and no
listing, so no check in this document applies to them and none ever should. If
you are looking for the rule that keeps a built-in running, it is in the daemon
(task 3.8), not here.

## Levels

| Level | What it costs |
|---|---|
| `error` | The release is not listed. Nothing publishes until it is fixed. |
| `review` | Held for a maintainer. Not a rejection — a decision the bot is not entitled to make. |
| `warn` | Listed anyway, and said out loud. |
| `note` | Something the bot did **not** decide. Printed on every run, passing or not. |

The three events that take a human are the first listing of a plugin, a
repository change, and (from task 3.5) a newly requested high-risk permission.
Everything else about a conforming release is zero-touch.

## Exit codes

`0` listed · `1` refused · `3` held for a maintainer · `2` the bot itself
failed. The last is deliberately distinct: "your plugin is bad" and "our tooling
is bad" must never render as the same comment to a stranger.

## Failing closed, today

`registry/v1/root.json` ships with **no root keys** — the ceremony in
`SECURITY.md` has not been run — so there is no root-signed `trust.json`, no
reusable-workflow allowlist, and every ingest stops at
`E_TRUST_UNPROVISIONED`. That is the same state `astra-daemon` compiles in
with an empty `PRODUCTION_ROOT_KEYS`, and it is correct on both sides: a trust
chain whose anchor does not exist must verify nothing rather than everything.

## What none of this proves

Three of these checks are heuristics, and describing them as anything more would
be worse than not having them.

**The host-RPC scan is a string search.** It looks in the bundle's *author
source* for the names of `PluginHostService` methods the manifest does not
declare, and fails the release for four of them —
`FireTrigger`, `SendChatMessage`, `SetVariable`, `SetThemeContribution` —
because each acts outside the plugin, on the user's session. It **catches
accidents, not a determined attacker**: anyone who does not want to be found
splits the literal in two, base64s it, or assembles it at runtime. Its scope is
also narrower than it looks, and for a good reason: the Python SDK's
`plugin_pb2.py` carries the name of every method of every service in the
proto, and a compiled Rust or Go plugin links a client whose stubs carry the
gRPC path string for each method whether the author calls it or not. So vendored
and generated files are skipped entirely, and a hit inside a compiled file is
recorded as a warning with the reason it is not evidence. The note row
`N_HOST_RPC_SCAN_SCOPE` prints on every run so a clean scan is never read as
"this plugin makes no undeclared calls".

**The typosquat fold catches lookalikes, not lookalike-designers.** NFKC,
case folding, hyphen stripping and a small confusable table; an exact collision
after folding is refused, one edit away is handed to a person. Someone who reads
`tools/lib/ids.mjs` and picks a name outside the fold table gets past it. What
happens then is reports and revocation, which is slower and is the honest
answer.

**The trademark list is a denylist**, with everything a denylist implies. It
refuses an id that *is* a mark or *leads* with one, and a display name whose
first word is one. It does not refuse `music-for-spotify`, because saying which
service you integrate with is what an honest third-party plugin does. It does
not know about transliterations, homoglyphs outside the fold table, or marks
nobody has added to `bot/policy/trademarks.json`.

And, above all: **none of this makes a plugin safe to run.** A verified,
attested, perfectly-provenanced plugin is code the user is choosing to execute
on their own machine, from an author whose GitHub account could itself be
compromised — a case PRODUCTION_PLAN §5.5 lists with the mitigation "nothing
cryptographic". What the bot proves is *who published these exact bytes*, and
that is all it proves.

## Ownership: one file, and why it is the one

**Commit `.well-known/astra-plugin-owner` to your default branch with your
GitHub login on a line of its own.** That is the whole thing:

```
mkdir -p .well-known
echo YOUR-GITHUB-LOGIN > .well-known/astra-plugin-owner
```

One login per line, `#` starts a comment, a leading `@` is forgiven. The
listing form asks for it *before* you submit, and the bot re-reads it from the
default branch on every run that consults it — so removing a line stops that
login opening a new listing request or passing a `/recheck`, and no CI runs.

**What it proves, exactly:** that somebody who can write to that repository's
default branch vouches for that login. It is a proof of **write access**, not of
legal ownership, not of authorship, and not of identity. Two things make that
enough for what this check is for — keeping a stranger from listing somebody
else's plugin and becoming the account its updates arrive through. A stranger
cannot land a commit on somebody else's default branch; and because the file is
read live, an author removed from an organisation stops being able to submit
the moment the file is updated. That last point has a boundary worth stating:
it governs a first listing and a `/recheck`, and not an already-listed plugin,
whose later releases are proved against the account that published the release
(second bullet below). Its residual risk is stated rather than hidden: a
contributor can open a pull request that adds their own login, and a maintainer
who merges it without reading has vouched for them. The registry cannot close
that, because the same merge could change the release workflow or the plugin's
source — anyone who can land commits on the default branch is already that
plugin's update path.

Two other methods exist, and it matters that **neither of them can fire for an
honest first submission**:

- `GET /repos/{owner}/{repo}/collaborators/{user}/permission` returning
  `admin` or `maintain` is tried **first**, as a free shortcut: one request,
  nothing for the author to do. GitHub answers it only for a caller that can
  already see the repository, and the bot's token belongs to `astra-registry`
  — so for any repository this registry does not itself own the answer is
  **403**, observed in a real run on 2026-08-14, and there is nothing an author
  can install to change that. A 403 means *the bot cannot see*, never *no*, and it is
  never printed as a finding against a submitter. A **200** is different and is
  final in both directions: `admin`/`maintain` grants, anything else is
  GitHub answering the exact question about the exact person, and the owner file
  does not overrule it.
- The account that **published the release** being listed. On a first listing it
  is inert, and structurally so: the documented `plugin-release.yml` creates
  the Release, so its author is `github-actions[bot]` and never a person. It
  is kept because it is the arm that carries every *later* release — a
  `/release` ping and the cron backstop prove ownership against the release's
  own author (`bot/lib/notify.mjs`, `resolveSubmitter`), where the protection
  comes from the repository already being listed and pinned. It is capped at 90
  days so that "they had access once" cannot stand in for "they have access", and
  it is left out of a first-listing refusal entirely, because a line about who
  pressed a button in CI is not something an author can act on.

A challenge file carrying a nonce is deliberately **not** used. It proves that
at some moment somebody could write to a branch, and then keeps proving it
forever; the owner file makes the same claim continuously and can be withdrawn.

## Every code

### The two facts a person types

The repository and the release tag. Nothing else is typed, so nothing else can be typed wrongly.

| Code | Level | Meaning | What to do |
|---|---|---|---|
| `E_INPUT_REPO` | error | The source repository is not `owner/name` | Write it exactly as GitHub does: `you/dice-roller`. No URL, no trailing slash, no branch. |
| `E_INPUT_TAG` | error | The release tag is not a tag | Copy the tag from the release page — `v0.2.0`, not a commit SHA and not a branch name. |

### Who is asking

Proved against the repository itself, live, at the moment of the request. See "Ownership" below for the one file this asks you to create.

| Code | Level | Meaning | What to do |
|---|---|---|---|
| `E_OWNERSHIP_UNPROVEN` | error | The repository has not vouched for the account asking | Commit `.well-known/astra-plugin-owner` on the repository's default branch with your GitHub login on a line of its own, then comment `/recheck`. One commit, no CI: `mkdir -p .well-known && echo YOUR-LOGIN > .well-known/astra-plugin-owner`. That file is the proof this registry asks for: it says somebody who can write to that branch vouches for this login — a proof of write access, not of legal ownership — and it is read live on every run, so deleting a line stops that login opening a new request or passing a `/recheck`. The bot also tries a free shortcut first (`GET /collaborators/{you}/permission`, which grants on `admin` or `maintain`), but GitHub answers that only for a caller that can already see the repository, so for any repository this registry does not itself own it is told nothing at all — a limit of the bot's token, not a finding about you, and not something you can install your way around. |

### The release and its assets

That the release exists, that the URLs belong to the repository being listed, and that the bytes are the bytes the release advertised.

| Code | Level | Meaning | What to do |
|---|---|---|---|
| `E_RELEASE_NOT_FOUND` | error | That repository has no release with that tag | Publish the release (a draft is invisible to everyone but you) and check the tag spelling. The bot reads it unauthenticated, so a private repository looks the same as a missing one. |
| `E_NO_BUNDLE_ASSETS` | error | The release carries no `.astraplugin` asset | `astra-plugin build` produces one file per target; attach every one of them to the release. The reusable release workflow does this for you. |
| `E_ASSET_URL_FOREIGN` | error | An asset URL does not belong to the repository being listed | Every download URL must sit under `https://github.com/<owner>/<repo>/releases/download/<tag>/`. This is the one check a user's daemon can make locally that ties the bytes to the repo, so a listing that fails it here would fail there too. |
| `E_ASSET_FILENAME` | error | The asset is not named `<id>-<version>-<target>.astraplugin` | `astra-plugin build` names bundles that way and the reusable release workflow asserts it. A different name is usually one of two real mistakes: a stale bundle left over from the previous version, or one build leg's file uploaded under another leg's name. Neither is caught by the digest, because the digest is taken of whatever was uploaded. |
| `E_ASSET_HEAD_FAILED` | error | The asset could not be fetched | Re-upload it and comment `/recheck`. If the release is private or the asset was deleted, nothing downstream can run. |
| `E_ASSET_SIZE` | error | The asset changed size between the listing and the download | Do not overwrite a published release asset. Cut a new version instead — a digest that moves is a digest that pins nothing. |
| `E_ARTIFACT_TOO_LARGE` | error | The bundle is over the size cap | See `policy/limits.json`. Ship models and datasets as a download the plugin fetches on first run, not inside the bundle. |
| `E_DIGEST_MISMATCH` | error | The bytes do not hash to what the attestation covers | The file at the URL is not the file CI built. Re-run the release workflow; if it happens twice, treat the repository as compromised before you treat it as a bug. |

### Who built the bytes

The half that makes the registry a trust boundary rather than a consistency checker.

| Code | Level | Meaning | What to do |
|---|---|---|---|
| `E_ATTESTATION_MISSING` | error | The bundle has no build attestation | Build it in GitHub Actions with `actions/attest-build-provenance`, which the Astra reusable release workflow already does. A hand-built bundle is refused however good it is: CI is the only signer, so an author's compromised laptop cannot publish. |
| `E_ATTESTATION_INVALID` | error | The attestation does not verify | Re-run the release workflow. Do not re-upload the asset by hand — the attestation covers the exact bytes, and hand-uploading is how they stop matching. |
| `E_ATTESTATION_UNCHECKED` | error | The attestation could not be checked — this is not about your release | Nothing to fix and nothing to rebuild: the verifier could not start. `gh attestation verify` fetches Sigstore's trust root before it can check anything, and when that fetch fails it reports a failure that reads like a bad signature. Comment `/recheck` — the same bytes usually verify on the next run. It still blocks, because an artifact nobody could verify must not be listed; it blocks as "we could not look", not as "we looked and it was wrong". |
| `E_ATTESTATION_SUBJECT_MISMATCH` | error | The attestation is for different bytes | The asset was replaced after CI attested it. Cut a new release; never overwrite an asset in place. |
| `E_RELEASE_COMMIT_MISMATCH` | error | The Release points at a different commit than the one that built it | `release.target_commitish` and the commit named in the build attestation must be the same. They are not, which means the Release was created against — or re-pointed at — a tree that did not produce these bytes. This matters beyond tidiness: the listing records that commit as the release's provenance, and every relative image in your README is pinned to it, so a mismatch renders pictures from a tree nothing attested. Re-create the Release at the commit the workflow built (`gh release create <tag> --target <sha>`), or re-run the release workflow on the tag. |
| `E_ATTESTATION_REPO_MISMATCH` | error | The attestation was issued to another repository | The bundle was built somewhere other than the repository being listed. That is exactly the case this check exists to catch. |
| `E_WORKFLOW_NOT_ALLOWED` | error | The build ran a release workflow this registry does not allow | Call the Astra reusable release workflow and pin it by commit SHA (`uses: mihailinl/AstraPlugins/.github/workflows/plugin-release.yml@<sha>`). Verifying an attestation without pinning which workflow produced it proves only that GitHub built something. The allowed SHAs live in the root-signed `trust.json`; adding one is a root-key ceremony, not a pull request. |
| `E_TRUST_UNPROVISIONED` | error | This registry has no root-signed trust document yet | Nothing a submitter can do — the root-key ceremony (SECURITY.md) has not been run, so there is no allowlist to check a workflow against. The bot fails closed rather than accepting a build it cannot place. |

### The archive's shape

Decided from the bytes alone, without extracting anything.

| Code | Level | Meaning | What to do |
|---|---|---|---|
| `E_BUNDLE_UNREADABLE` | error | The archive cannot be read | Rebuild with `astra-plugin build`. A truncated upload is the usual cause. |
| `E_BUNDLE_TOO_MANY_ENTRIES` | error | Too many files in the archive | The daemon refuses to extract it, so listing it would publish something uninstallable. See `policy/limits.json`. |
| `E_BUNDLE_TOO_LARGE_EXTRACTED` | error | The archive expands past the extraction cap | Same cap the daemon enforces. Shrink the payload or fetch it at runtime. |
| `E_BUNDLE_DUPLICATE_ENTRY` | error | Two archive entries share a name | Rebuild. The second copy would overwrite a file that already matched the manifest, after it was verified. |
| `E_BUNDLE_ABSOLUTE_PATH` | error | An entry is an absolute or Windows-style path | Bundle paths are relative and use `/`. Rebuild with `astra-plugin build` rather than a hand-made zip. |
| `E_BUNDLE_TRAVERSAL` | error | An entry contains `..` | Rebuild. A `..` component is how an archive writes outside the directory it was extracted into. |
| `E_BUNDLE_ADS` | error | An entry name contains `:` | Rename the file. On Windows `:` opens an NTFS alternate data stream, so the bytes land somewhere nothing looks. |
| `E_BUNDLE_TRAILING_DOT` | error | An entry name ends in a dot or space | Rename it. Windows strips both silently, so the name in the manifest and the name on disk stop being the same string. |
| `E_BUNDLE_SYMLINK` | error | The archive contains a symlink | Ship the file itself. A symlink's target is not covered by any of the checks its path passes. |
| `W_BUNDLE_DUPLICATE_ENTRY_CASE` | warn | Two entries differ only in letter case | Rename one. Linux keeps both; Windows and macOS keep one, and the daemon refuses the bundle there — so this lists cleanly and then fails to install for most of your users. |
| `E_PLUGIN_TOML_MISSING` | error | The bundle has no `plugin.toml` | Every plugin carries one; it is what the daemon reads to know what the plugin is. Rebuild with `astra-plugin build`. |
| `E_MANIFEST_MISSING` | error | No `MANIFEST.json` — this is not a v2 bundle | Rebuild with a current `astra-plugin`. |
| `E_MANIFEST_NOT_FIRST` | error | `MANIFEST.json` is not the first archive entry | The daemon reads it from byte zero. Rebuild rather than repacking by hand. |
| `E_MANIFEST_COMPRESSED` | error | `MANIFEST.json` is compressed | It must be stored uncompressed so it can be read without inflating attacker-supplied bytes. |
| `E_MANIFEST_INVALID` | error | `MANIFEST.json` is malformed | Rebuild with `astra-plugin build`. |
| `E_MANIFEST_ID_MISMATCH` | error | The manifest names a different plugin | One release, one plugin. A bundle whose manifest names another id installs as that other id. |
| `E_MANIFEST_VERSION_MISMATCH` | error | The manifest names a different version | Retag and rebuild so the tag, the manifest and the filename agree. |
| `E_MANIFEST_PLATFORM_UNKNOWN` | error | The manifest's platform has no registry key | `os`/`arch` must be one of the pairs in `tools/lib/platform.mjs`. |
| `E_MANIFEST_PLATFORM_MISMATCH` | error | Two artifacts of this release claim the same platform | Each target gets its own file. Check the build matrix. |
| `E_MANIFEST_UNSORTED` | error | `MANIFEST.files` is not sorted by path | Rebuild. The order is part of the format so two builders produce the same bytes. |
| `E_MANIFEST_EXTRA_FILE` | error | The archive holds a file the manifest does not list | An unlisted file is a file nothing verifies — at install, and at every start afterwards. Rebuild. |
| `E_MANIFEST_MISSING_FILE` | error | The manifest lists a file the archive does not hold | Rebuild; the manifest and the archive were produced from different trees. |
| `E_MANIFEST_SIZE_MISMATCH` | error | A file's size disagrees with the manifest | Rebuild. The archive was edited after the manifest was written. |
| `E_MANIFEST_HASH_MISMATCH` | error | A file's content disagrees with the manifest | Rebuild. If the build is reproducible and this persists, the release asset was tampered with after CI. |
| `E_MANIFEST_HEADER_DISAGREE` | error | The archive holds two different `MANIFEST.json`s | The manifest the central directory points at is not the one at byte zero, and the daemon reads byte zero. This is not something a build tool does by accident. |
| `E_MANIFEST_LOCAL_HEADER` | error | `MANIFEST.json` cannot be read from byte zero | Rebuild with `astra-plugin build`. |
| `W_MANIFEST_MODE_MISMATCH` | warn | A file's recorded mode differs from the archive's | The daemon applies the manifest's mode and refuses the mismatch, so this lists and then does not install. Rebuild. |
| `E_PERMISSIONS_HASH_MISMATCH` | error | `permissions_hash` does not cover the declared permissions | Rebuild with `astra-plugin build`, which derives the hash from the permissions and cannot emit a mismatch. Astra refuses to install this bundle (§5.3-D, block code PERMISSIONS_HASH_MISMATCH), so listing it would advertise a version nobody can have. The hash is what the consent sheet renders against and what the update gate compares: when it does not cover the permission map, a user can approve one list while the daemon enforces another. |
| `W_LEGACY_SIGNATURE_ENTRY` | warn | The bundle carries a legacy in-ZIP `SIGNATURE`/`PUBKEY` | Harmless and ignored. It is never a trust signal here — trust comes from the attestation and from this registry's countersignature. `astra-plugin build` stops writing it. |
| `E_ENTRY_MISSING` | error | `entry.command` is missing | Declare the program the daemon should run. |
| `E_ENTRY_ABSOLUTE` | error | `entry.command` is an absolute path | It must be relative to the install directory, or the name of a declared runtime. |
| `E_ENTRY_TRAVERSAL` | error | `entry.command` escapes the install directory | Point it at a file inside the bundle. |
| `E_ENTRY_SHELL` | error | `entry.command` is a shell | Run your program directly. A shell as the entry point means the daemon executes whatever `args` say, which is arbitrary code with none of the review the rest of this list applies. |
| `E_ENTRY_NOT_IN_BUNDLE` | error | `entry.command` is neither a bundled file nor a declared runtime | Ship the binary in the bundle, or name `python` / `node` / `deno` / `bun`. |

|---|---|---|---|

| `E_PROBE_UNAVAILABLE` | error | The manifest probe could not be run | A bug in this registry, not in your plugin. `plugin.toml` was not validated by anything, so the run fails closed. |

### Whether the name is already taken, or dressed as someone else's

A heuristic. Read the caveat below before citing it as a defence.

| Code | Level | Meaning | What to do |
|---|---|---|---|
| `E_ID_RESERVED` | error | That id is reserved | See `policy/reserved-ids.json`. Ids that read as first-party are an impersonation primitive. |
| `E_ID_RESERVED_PREFIX` | error | That id uses a reserved prefix | `astra-`, `official-` and `verified-` are first-party only. |
| `E_TYPOSQUAT_COLLISION` | error | The id is indistinguishable from a listed plugin | After NFKC normalisation, case folding, hyphen stripping and confusable folding it is the same string as an existing listing. Two cards a user cannot tell apart cannot both exist. Pick a different name. |
| `E_TRADEMARK` | error | The id or display name claims someone else's mark | Name it for what it does, not for the service it talks to: `telegram-client` becomes `tg-bridge`, `Spotify Controller` becomes `Music Controller for Spotify` only with the rightsholder's say-so. See `bot/policy/trademarks.json`. |
| `R_TYPOSQUAT_NEAR` | review | The id is one edit away from a listed plugin | Held for a human, not rejected — plenty of honest names are near-misses. If it is deliberate, say so in the issue and it will be approved faster. |
| `R_DISPLAY_NAME_COLLISION` | review | The display name matches a listed plugin's, bar case, spacing or lookalike letters | Held for a human. The store shows names, not ids, so two identical names are two identical cards. A byte-identical name counts: it is the strongest form of the collision, not an exception to it. |
| `R_DISPLAY_NAME_MIXED_SCRIPT` | review | The display name mixes alphabets | Held for a human. Write the name in one alphabet. A name that borrows a single Cyrillic or Greek letter for its Latin shape renders as a name it does not contain, and the id charset cannot catch it because the id is not the string on the card. |

### What the store card will say

Length, licence, and text that renders as something other than what it contains.

| Code | Level | Meaning | What to do |
|---|---|---|---|
| `E_METADATA_UNSAFE_TEXT` | error | Metadata contains invisible or direction-changing characters | Remove the zero-width, bidi-override or control characters. They are what makes a card render as a name it does not contain. |
| `E_METADATA_TOO_LONG` | error | A metadata field is over its length cap | See `policy/limits.json`. The store's card has a fixed size; a longer string is truncated somewhere less pleasant. |
| `E_METADATA_MISSING` | error | `plugin.toml` does not say what the plugin is | Fill in `description` (and `author`). The store card is built entirely out of the bundle — there is no form to type a summary into, by design — so a manifest with no description produces a listing with nothing on it. |
| `E_LICENSE_MISSING` | error | `plugin.license` is empty | Declare an SPDX identifier. A plugin with no licence is code nobody may legally run. |
| `E_LICENSE_NOT_ALLOWED` | error | That licence is not on the allowlist | See `policy/spdx-allowlist.json`. It is an allowlist, not a denylist: a licence nobody here has read is one this registry cannot promise anything about. To add one, open a pull request with a sentence on why. |

### Whether this release may follow the last one

And whether a person has to look at it.

| Code | Level | Meaning | What to do |
|---|---|---|---|
| `E_VERSION_NOT_NEW` | error | That version is already listed, or is older than one that is | Releases go forward. Bump the version and cut a new release — a version that is republished with different bytes is how a downgrade attack starts. |
| `E_VERSION_INCONSISTENT` | error | The release's bundles do not agree on a version | One release, one version, every target. Check the build matrix. |
| `R_IDENTITY_CHANGED` | review | This plugin was listed from a different repository | Held for a human, always. A repository change is an author change until somebody says otherwise, and every installed copy carries a pin to the old one. |
| `R_FIRST_LISTING` | review | First listing for this plugin | A human reads the first one, once, ever. Later releases from the same repository are zero-touch. |

### Declared versus called host RPCs

A string search. Read the caveat below; it is not a sandbox.

| Code | Level | Meaning | What to do |
|---|---|---|---|
| `E_HOST_RPC_UNDECLARED` | error | Source in the bundle calls a high-risk host RPC the manifest does not declare | Declare the capability the call needs, or remove the call. The four that block are `FireTrigger`, `SendChatMessage`, `SetVariable` and `SetThemeContribution` — each of them acts on the user's session rather than inside your plugin. |
| `W_HOST_RPC_UNDECLARED` | warn | Source in the bundle names a host RPC the manifest does not declare | Not blocking. Declare the capability if the call is real; ignore this if the string is a comment or a log line. |
| `W_HOST_RPC_IN_OPAQUE_FILE` | warn | A compiled file contains a host RPC name | Not blocking, and usually not a call: a linked SDK client contains the name of every method on the service whether or not you invoke it. Named so it is on the record, not because it is evidence. |
| `R_HOST_RPC_IN_VENDOR_DIR` | review | One of the four acting-outside-the-plugin RPCs is named inside a `generated/` or `vendor/` directory | Held for a human. Those two directory names are chosen by whoever built the bundle, not by a toolchain, so the scan no longer skips them — but a real generated tree is a normal thing to ship. Declare the capability or permission if the call is yours, or say in the issue what wrote the file. |
| `W_HOST_RPC_IN_VENDOR_DIR` | warn | A non-blocking host RPC is named inside a `generated/` or `vendor/` directory | Recorded. Declare the capability if the call is yours. |
| `N_HOST_RPC_SCAN_SCOPE` | note | The RPC scan read source files only | Compiled binaries and vendored SDK code are not decidable by string matching. This check catches accidents; it does not catch anyone who is trying. |

### The listing the bot writes

Held to the same rules a hand-written listing is held to.

| Code | Level | Meaning | What to do |
|---|---|---|---|
| `E_DERIVED_LISTING_INVALID` | error | The listing the bot derived does not pass this repository's own validator | A bug in this registry, not in your plugin. Please leave the issue open. |
## Where each check lives

| File | What it owns |
|---|---|
| `bot/ingest.mjs` | The pipeline and the order of it |
| `bot/manifest-probe/` | `plugin.toml`, parsed by `astra-plugin-manifest` — the daemon's crate, linked, not reimplemented |
| `bot/lib/attestation.mjs` | `gh attestation verify`, and the root-signed workflow allowlist |
| `bot/lib/ownership.mjs` | `.well-known/astra-plugin-owner`, and the two methods that cannot replace it |
| `bot/lib/bundle.mjs` | The archive, read in memory and never extracted |
| `bot/lib/names.mjs` | Typosquatting and trademarks |
| `bot/lib/rpcscan.mjs` | The host-RPC heuristic and its scope |
| `bot/lib/derive.mjs` | The listing, written from the bundle |
| `bot/lib/codes.mjs` | This vocabulary. Renaming a code is a breaking change |
| `tools/validate.mjs` | The listing rules — shared with CI, so the bot and the merge gate cannot disagree |

## Testing it

`node bot/tests/ingest.test.mjs` runs the whole pipeline over the 27 shared
bundle vectors in `tests/vectors/` — vendored from
`AstraPlugins/testdata/bundles`, and shared with the CLI's suite and the
daemon's — plus one case per failure class, each asserting the code above. A
code that no test provokes is printed at the end of the run rather than being
quietly assumed to work.
